# /predict_attrition — 퇴사 위험 예측 → 결과 엑셀

어떤 프롬프트가 들어와도 아래 여섯 단계를 순서대로 밟는다. 1단계는 사람이 정하는 일이고, 2~6단계는 `scripts/predict_attrition.py`가 산출물을 만들며 이 스킬은 그것을 HR 담당자의 말로 옮긴다.

## 1. 질문 정의 — 대상·기간·모집단을 한 문장으로

요청을 "**기준일 이후 N일 이내 [어떤 퇴사] 위험을 [누구]에 대해 평가한다**"로 바꾼다.

- 기본값: 대상 `자발적 퇴사`, 기간 `90일`, 모집단 `기준일 현재 재직자 전원(휴직자 포함)`. 기준일은 입력 파일에서 읽는다.
- 요청에 단서가 있으면 반영한다. "개발팀 이탈이 걱정" → `--filter 직군=개발직`, "신입이 많이 나가" → `--filter`는 두지 않되 근속 가설(H3)에 주목, "내년 상반기" → `--horizon-days 180`.
- 요청이 모호하면 기본 정의를 **먼저 한 줄로 선언하고** 바로 진행한다. 대상(자발적/전체 퇴사)이나 모집단이 결과를 크게 바꿀 때만 한 번 확인 질문을 한다. 실제 요청 원문은 `--prompt`로 넘겨 기록한다.
- 민감 속성(성별·국적·혼인 등)으로 모집단을 자르는 요청은 공정성 문제를 한 줄로 알리고 거절한다. 필터 가능한 키: 본부, 팀, 직군, 직급, 고용형태, 재직상태, 직책.

## 2. 데이터 이해 — 무엇이 있고 무엇을 뜻하며 어디가 비었나

실행:

```bash
python <이 스킬 폴더>/scripts/predict_attrition.py --input <첨부.xlsx> --out <출력 폴더> \
  [--target "자발적 퇴사"] [--horizon-days 90] [--filter 직군=개발직] [--prompt "<요청 원문>"] [--spec analysis_spec.json]
```

스크립트가 테이블 목록(의미·행 수·직원 커버리지·기간), 중복 사번, 명단 밖 사번, 신호별 결측률, 계산하지 못한 신호를 `summary.json`의 `data_profile`에 적고 결과 엑셀 `2 데이터 이해`·`2 데이터 이슈` 시트에 남긴다. **기준일 이후에 효력·확정·신청된 기록은 이 단계에서 제외되고 제외 행 수가 기록된다.**

답변에서는 어떤 데이터(입사기록·월별 근태·평가 이력·보상·설문 등)를 썼고 무엇이 없었는지 두세 문장으로 말한다. 이슈가 있으면 그대로 전한다.

## 3. 가설 수립 — 무엇이 퇴사와 관련 있는가

아홉 가지 가설(H1 연장근로 증가, H2 평가 하락, H3 근속 1~3년, H4 보상 밴드 하단·미인상, H5 승진 보류, H6 설문 몰입·보상 인식·eNPS 저하, H7 근태 변화, H8 기간제·계약 만료, H9 휴가 반려·온콜)을 `summary.json`의 `hypotheses`와 `3 가설` 시트에서 읽는다.

- 라벨이 있으면 가설별 단변량 AUC로 **지지 / 반대 / 불명확**이 판정돼 있다. 그대로 전한다.
- 라벨이 없으면 판정은 **탐색(라벨 없음)**이다. 신호가 두드러진 인원 비율과 어느 팀에 몰렸는지만 말하고, "검증된 것이 아니라 규칙 지수에 가중치로 반영된 가설"이라고 분명히 한다. '높음' 그룹 동반 비율은 지수 구성 요소라 순환 참조이므로 근거로 내세우지 않는다.

## 4. 검증 — 반례, 누수, 산정 방식, 한계

`summary.json`의 `validation`과 `4 검증` 시트를 읽고 체크리스트를 표로 보여준다.

- **기준일 이후 정보 제외**: 테이블별 제외 행 수.
- **반례 확인**: "강한 신호인데 밴드 낮음", "밴드 높음인데 강한 단일 신호 없음" 건수와 예시. 신호 하나로 단정하면 안 된다는 뜻으로 설명한다.
- **점수 산정 방식**: 규칙 지수면 가중치·밴드 기준·분포, 모델이면 알고리즘·교차검증 AUC·표본 수.
- **순위 안정성**(규칙 모드): 신호를 하나 뺐을 때 순위 상관·밴드 변경 수. 특정 신호 하나에 결과가 좌우되는지 말한다.
- **한계**: `limitations`를 그대로 옮긴다. 라벨이 없으면 "정확도를 측정할 수 없다"를 반드시 포함한다.

## 5. 행동 연결 — HR이 추가로 확인할 사항

- 회사 전체 신호(`company_signals`)와 조치 제안(`actions`)을 3~5개.
- 팀별 확인 사항(`unit_actions`, `5 팀별 확인사항` 시트): 평균 위험 상위 팀마다 두드러진 신호와 "HR이 확인할 사항"(예: 업무량·인력 배치, 보류 사유 설명 여부, 경력 경로 논의).
- 상위 위험 직원 표(`top_employees`, 기본 10명): 사번·이름·팀·직급·근속·위험 지수·주요 신호(`drivers_plain`).
- 조치는 면담·보상 검토·업무량 조정·성장 기회 논의 같은 HR 조치로 한정한다. 개인 처분을 제안하지 않는다.

## 6. 재사용 — 같은 질문으로 다시 돌릴 수 있게

`analysis_spec.json`(질문 정의·모드·가중치·입력 조건·절차·검증 기준·출력 양식)이 함께 생성된다. 다음에 같은 분석을 하려면 `--spec analysis_spec.json`만 넘기면 된다고 안내한다. 가중치를 바꿨으면 그 파일에 기록된다.

## 답변 양식

1. 질문 정의 한 문장(기본값을 썼으면 그 사실 포함)
2. 데이터 이해 두세 문장 + 이슈
3. 가설 표(가설 / 판정 / 근거 한 줄)
4. 검증 체크리스트 표 + 한계
5. 결과: 밴드 분포 표, 팀별 상위 5, 상위 위험 직원 표, 회사 전체 신호·조치, 팀별 확인 사항
6. 파일 안내: `퇴사위험_결과.xlsx`(시트 구성 한 줄, `_data`/`_meta`는 대시보드용이니 삭제 금지), `analysis_spec.json`, 대시보드는 `/make_dashboard`

규칙 기반 모드면 어디서든 "지수(0~1)와 밴드"로만 말하고 "퇴사 확률 n%"라고 하지 않는다. 직원 개인의 성향·태도를 단정하지 않으며, 신호는 "확인해 볼 지점"이다.
