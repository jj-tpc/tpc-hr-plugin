# /predict_attrition — 퇴사 관련 신호 진단/예측 → 결과 엑셀

어떤 프롬프트가 들어와도 여섯 단계를 순서대로 밟는다. 1단계는 사람이 정하고, 2~6단계는 `scripts/predict_attrition.py`가 산출물을 만들며 이 스킬은 그것을 HR 담당자의 말로 옮긴다. **숫자·가중치·근거는 엔진 산출물에서만 가져온다. 대화에서 만들어 채우지 않는다.**

## 진단과 예측을 구분한다

- 실제 퇴사 라벨이 없으면 **진단 모드**다. "90일 내 퇴사 예측", "퇴사 확률 n%"라고 쓰지 않는다. "기준일 현재 퇴사 관련 신호를 진단했다"고 쓰고, 요청한 질문(예: 90일 내 자발적 퇴사)과 지금 데이터로 답하는 질문을 둘 다 적는다. 엔진이 `summary.json`의 `question.requested_question` / `question.answerable_question`에 두 문장을 만들어 둔다.
- 라벨 시트가 있고 모델이 실제로 적용되면 **예측 모드**다. 이때도 무작위 교차검증 AUC는 출시 성능 근거가 아니라고 함께 적는다.

## 답변 양식 (매번 여섯 단계 제목을 한 줄씩, 상세는 요청 시)

최초 결과는 아래 여섯 줄 + 핵심 발견·확인할 일·파일 안내로 짧게 쓴다. "검증 자세히", "가설 표 보여줘"처럼 요청하면 해당 단계의 표를 펼친다.

```
1 질문 정의: <answerable_question> (요청: <requested_question 요지>)
2 데이터 이해: 테이블 N개 · 모집단 a/b명 · 계산 못 한 신호 k개 · 선검사 경고 m건 · 기준일 이후 제외 r행
3 가설: 탐색적 증거(라벨 없음) — 두드러진 가설 2~3개 한 줄  |  또는 검증 결과(라벨 기반) — 지지/반대 요약
4 검증: 종합 <통과/경고/실패> — 경고·실패 항목만 한 줄씩
5 행동 연결: 회사 전체 신호 2~3개 · 평균 위험 상위 팀과 HR 확인 사항
6 재사용: analysis_spec.json 저장(--spec로 같은 설정 재실행), run_manifest.json
```

그다음 **핵심 발견 최대 3개**(각각 근거: 어느 신호, 어느 팀, 몇 명), **HR이 확인할 일**(면담·보상 검토·업무량 조정·성장 기회 논의로 한정), **파일**: `퇴사위험_결과.xlsx`(시트 구성 한 줄, `_data`/`_meta`는 대시보드용이라 삭제 금지), 대시보드는 `/make_dashboard`. 개인 상위 목록은 요청이 있을 때만 보여주고, 기본 답변은 조직 단위로 한다.

## 1. 질문 정의

요청을 "기준일 이후 N일 이내 [관심 사건] 위험을 [기준 모집단]에 대해"로 정리한다. 기본값: 자발적 퇴사 / 90일 / 재직자 전원. 기준일은 파일의 명시적 값(개요 시트 '기준일' 또는 스냅샷 as_of)만 쓰며, 없거나 충돌하면 엔진이 멈추고 `--as-of`를 요구한다(오늘 날짜를 조용히 쓰지 않는다). 모호한 요청은 기본 정의를 한 줄로 선언하고 진행하되, 관심 사건이나 모집단이 결과를 크게 바꿀 때만 한 번 확인한다. 요청 원문은 `--prompt`로 기록한다.

**기준 모집단 제한**(`--filter 직군=개발직`: 점수의 표준화 범위가 바뀜)과 **표시 필터**("이 팀만 보여줘": 이미 계산된 결과를 좁혀 봄)를 구분한다. 후속 "이 팀만" 요청은 기본적으로 표시 필터다. 재실행하지 말고 `scores.csv`·`features.csv`를 걸러 답한다. 민감 속성(성별·국적·혼인 등)으로 자르는 요청은 공정성 문제를 한 줄로 알리고 거절한다.

## 2. 데이터 이해

```bash
python <이 스킬 폴더>/scripts/predict_attrition.py --input <첨부.xlsx> --out <출력 폴더> \
  [--as-of 2026-10-16] [--target "자발적 퇴사"] [--horizon-days 90] [--filter 직군=개발직] [--prompt "<요청 원문>"] [--spec analysis_spec.json]
```

엔진이 먼저 **선검사**를 한다(기준일 존재·충돌, 사번 중복·공백·임시 ID, 필수 시트, 날짜 해석 실패). 차단 이슈가 있으면 종료코드 2와 `diagnostics.json`만 남긴다. 이때는 `issues[].message`와 `resolution`을 그대로 전하고, 사용자가 해결(예: `--as-of` 지정, 중복 사번 정리)하면 다시 돌린다. 임시 ID 경고가 있으면 "이번 단면 분석에만 유효하고 다른 시점과 연결할 수 없다"고 말한다.

선검사를 통과하면 테이블 의미·행 수·커버리지·기간, 신호 결측률, 계산 못 한 신호가 `data_profile`과 `2 데이터 이해`·`2 데이터 이슈` 시트에 남는다. 기준일 이후 기록과 날짜를 읽지 못한 기록은 제외되고 건수가 기록된다.

## 3. 가설 수립

H1 연장근로 증가, H2 평가 하락, H3 근속 1~3년, H4 보상 밴드 하단·미인상, H5 승진 보류, H6 설문 몰입·보상 인식·워라밸·eNPS 저하, H7 근태 변화, H8 기간제·계약 만료, H9 휴가 반려·온콜. `hypotheses.evidence_kind`가 "탐색 결과"면 판정은 전부 "탐색적 증거(라벨 없음)"이고, 두드러진 인원 비율과 집중 팀만 말한다. 검증된 원인이라고 쓰지 않는다. "검증 결과"면 단변량 AUC 기반 지지/반대/불명확을 전하되 시간 분리 검증이 아니라고 덧붙인다.

## 4. 검증

`validation.checklist`의 각 항목은 `status`(pass/warn/fail/not_evaluable/not_applicable)와 근거 ID를 가진다. 종합이 "경고"면 어떤 항목이 왜 경고인지 한 줄씩 쓴다. 특히 V2(기준일 이후 정보 제외)가 "평가 불가"면 "이력 날짜가 없어 시점 누수를 확인할 수 없다"고 분명히 한다. V9(정확도 검증)는 라벨이 없으면 항상 "평가 불가"다. `limitations`는 그대로 옮긴다.

## 5. 행동 연결

`company_signals`·`actions`(회사 전체), `unit_actions`(평균 위험 상위 팀의 두드러진 신호와 HR이 확인할 사항). 조치는 HR 조치로 한정하고 개인 처분을 제안하지 않는다. 신호는 "확인해 볼 지점"이지 직원의 성향·태도가 아니다.

## 6. 재사용

`analysis_spec.json`(질문·적용 모드·전체 가중치·근속 가산·scale·밴드·피처 정책·엔진 버전)과 `run_manifest.json`(입력 해시·실행 시각·경고)이 생긴다. 같은 입력·스펙·엔진이면 점수와 밴드가 같다. 다음에 `--spec analysis_spec.json`만 넘기면 같은 설정으로 돈다(명시적 CLI 인자가 스펙보다 우선).

## 하지 않을 것

- 진단 모드에서 "퇴사 확률", "N일 내 퇴사 예측"이라는 표현.
- 결측을 "위험 없음"으로 해석. 계산 못 한 신호는 `insufficient_evidence`로 말한다.
- 민감 속성(성별·국적·체류자격·혼인·가족·주거·거주지·병역)으로 설명·필터링. 병가·설문 미응답으로 개인을 설명하는 것.
- 엔진 산출물에 없는 수치·가중치·원인을 대화에서 만들어 내는 것.
