# 분석 방법론 규격: 질문 → 데이터 → 가설 → 검증 → 행동 → 재사용

이 문서는 `/predict_attrition`이 어떤 요청에도 같은 순서로 일하게 하는 규격이다. 스크립트가 만드는 산출물과 1:1로 대응한다.

## 입력 조건

| 항목 | 조건 |
|---|---|
| 파일 | HR xlsx 1개. 표준 HR 워크북(`hr_*`, `v_*` 시트) 또는 직원 명부 한 장(첫 시트 1인 1행) |
| 필수 정보 | 직원 식별자(사번), 최소한 소속·직급·입사일 중 일부 |
| 선택 정보 | 보상 이력, 평가 이력, 월별 근태, 승진 심사, 인사발령, 휴가 신청, 교육, 온콜, 설문 |
| 라벨(선택) | `퇴사라벨`/`labels` 시트 또는 `퇴사여부` 컬럼: `employee_id, left(0/1)`. 양성·음성 각 10명 이상이면 모델 모드 |
| 금지 | 성별·국적·체류자격·혼인·가족·주거·거주지·병역은 어떤 단계에서도 쓰지 않는다 |

## 분석 모드(제품 수준)와 계산 방식

| 분석 모드 | 조건 | 표현 |
|---|---|---|
| `diagnostic` 진단 | 라벨 없음(기본) | "기준일 현재 퇴사 관련 신호를 진단한다". 요청한 질문(예: 90일 내 자발적 퇴사)은 기록만 하고 예측하지 않는다 |
| `change` 변화 비교 | 두 기준일 스냅샷(P2 예정) | "두 시점 사이 신호 변화를 비교한다" |
| `predictive` 예측 | 라벨 시트 + 모델이 실제 적용 | "N일 이내 퇴사 확률을 예측한다(검증된 라벨 기반)". 무작위 교차검증 AUC는 출시 성능 근거가 아님을 함께 적는다 |

계산 방식 `heuristic / model / auto`는 별도 설정이다(`mode_requested` → `mode_applied`).

## 입력 선검사(피처 계산 전)

| 코드 | 심각도 | 뜻 |
|---|---|---|
| AS_OF_MISSING / AS_OF_CONFLICT | 차단 | 기준일이 없거나 파일 안에서 다르다 → `--as-of` 지정. 오늘 날짜를 자동으로 쓰지 않는다 |
| ID_DUPLICATE / ID_BLANK / ID_MISSING / STRUCTURE_MISSING | 차단 | 사번 중복·공백·컬럼 없음·직원 시트 없음 → `diagnostics.json`에 해결 방법 기록, 종료코드 2 |
| ID_TEMPORARY | 경고 | 사번 없이 임시 ID. 단면 분석만 가능, 시점·파일 간 연결 불가 |
| DATE_PARSE_FAIL | 경고 | 날짜로 읽지 못한 값. 해당 행은 피처 계산에서 제외 |
| ID_LEADING_ZERO / DATE_AFTER_AS_OF | 정보 | 선행 0 사번 유지, 기준일 이후 기록 제외 건수 |

## 분석 절차와 산출물

| 단계 | 하는 일 | 산출물(summary.json 키 / 결과 엑셀 시트) |
|---|---|---|
| 1 질문 정의 | 대상·기간·모집단·기준일을 한 문장으로. 기본: 자발적 퇴사 / 90일 / 재직자 전원 | `question`, `population` / `1 질문 정의` |
| 2 데이터 이해 | 테이블 의미·행 수·커버리지·기간, 중복·명단 밖 사번, 신호 결측률, 계산 불가 신호. 기준일 이후 기록 제외 | `data_profile` / `2 데이터 이해`, `2 데이터 이슈` |
| 3 가설 수립 | H1~H9 가설을 신호에 연결. 라벨 있으면 단변량 AUC 판정, 없으면 분포 탐색 | `hypotheses` / `3 가설` |
| 4 검증 | 누수(기준일 이후 제외 행 수), 반례(강한 신호·낮은 밴드 등), 산정 방식 공개, 순위 안정성(신호 제거 감도), 커버리지, 한계 | `validation` / `4 검증` |
| 5 행동 연결 | 회사 전체 신호·조치, 팀별 두드러진 신호와 HR 확인 사항, 상위 위험 직원과 평이한 신호 | `company_signals`, `actions`, `unit_actions`, `top_employees` / `5 팀별 확인사항`, `회사 전체 신호`, `조치 제안`, `직원별 위험` |
| 6 재사용 | 질문·모드·가중치·입력 조건·절차·검증 기준·출력 양식을 스펙으로 저장. `--spec`로 재실행 | `analysis_spec.json` |

## 검증 기준(체크리스트)

각 항목은 실제 검사로 `pass / warn / fail / not_evaluable / not_applicable`과 근거 ID를 산출한다. 상수로 "통과"를 적지 않는다.

| ID | 항목 | 상태 기준 |
|---|---|---|
| V1 | 기준일 출처 | 파일의 명시적 값 또는 사용자 지정이면 pass, 없으면 fail |
| V2 | 기준일 이후 정보 제외 | 날짜 컬럼을 검사해 이후 행을 제외했으면 pass, 읽지 못한 날짜가 있으면 warn, 검사할 날짜 컬럼이 없으면 not_evaluable |
| V3 | 민감 속성·제외 신호 미사용 | 피처 테이블과 실제 사용 신호에 민감 속성(성별·국적·혼인…)이나 개인 제외 신호(병가·설문 미응답)가 있으면 fail |
| V4 | 점수 산정 방식 공개 | 규칙: 가중치·근속 가산·scale·밴드. 모델: 알고리즘·CV AUC·양성 수 |
| V5 | 반례 확인 | "강한 신호인데 밴드 낮음", "밴드 높음인데 강한 단일 신호 없음" 건수·예시가 있으면 pass, 전혀 없으면 warn |
| V6 | 순위 안정성 | 신호 하나 제거 시 순위 상관 ≥0.8이면 pass, 미만이면 warn. 모델 모드는 not_applicable |
| V7 | 사용 신호 커버리지 | 사용 신호 중 커버리지 50% 미만이 있으면 warn |
| V8 | 입력 선검사 | 경고 이슈가 있으면 warn |
| V9 | 정확도 검증 | 라벨 없으면 not_evaluable. 라벨 있어도 무작위 CV는 warn(시간 분리 평가가 아님) |

## 출력 양식

- `퇴사위험_결과.xlsx`: `1 질문 정의` → `요약` → `2 데이터 이해` → `2 데이터 이슈` → `3 가설` → `4 검증` → `5 팀별 확인사항` → `직원별 위험` → `팀별` → `회사 전체 신호` → `조치 제안` → `신호 상세` → `신호 설명` → `_data` → `_meta`
- `summary.json`: 위 표의 키 + `bands`, `by_division`, `top_units`, `caveats`, `unavailable_signals`
- `analysis_spec.json`(스키마 hr-attrition-spec/2): 질문·요청/적용 모드·전체 가중치·근속 가산·scale·밴드·피처 정책·엔진 버전. 같은 입력·스펙·엔진이면 점수·밴드 동일. 우선순위 명시적 CLI > 스펙 > 기본값
- `run_manifest.json`: run_id, 입력 해시, 스펙 해시, 실행 시각, 엔진 버전, 경고(실행별 값. 해시는 익명화 수단이 아님)
- `diagnostics.json`: 선검사 이슈(차단 시 이것만 생성)
- `scores.csv`, `features.csv`, `metrics.json`: 분석가용 원자료
- 대시보드는 `/make_dashboard`가 `퇴사위험_결과.xlsx`(+원본)로 만든다

## 표현 규칙

- 규칙 모드에서는 "위험 지수(0~1)·밴드"로 말하고 "퇴사 확률"이라 하지 않는다.
- 가설 판정이 "탐색(라벨 없음)"이면 "검증되지 않은 가설을 가중치로 반영했다"고 쓴다.
- 신호는 "확인해 볼 지점"이며 개인의 성향·태도가 아니다.
